# agentc design (v0)

This document records the decisions behind agentc and the questions still open. The [README](../README.md) describes what agentc is; this explains why it is shaped that way.

## Goal

A developer can use Claude Code, OpenCode, pi or oh-my-pi. Whatever they use, they can spawn the same agents, defined once, through that harness's **native** subagent mechanism, with tool and skill allowlists the harness itself enforces.

## Decisions

### Compile to native, don't spawn

We considered a harness-agnostic spawner: a CLI or MCP server that launches child agents in headless mode (`claude -p`, `opencode run`, `pi -p`) and normalizes their output. We rejected it for v0:

- Restrictions must be enforced by the harness itself. A separately launched process cannot inherit or prove the harness's permission model.
- Native subagents keep the harness's progress UI, cost tracking and prompt caching.
- Spawning needs no new code at all: each harness already has a way to start a subagent.

So agentc is a compiler and installer, not a runtime.

### Deny by default, strict by default

Allowlist semantics differ between harnesses. Some deny everything not listed; others allow anything not mentioned, and an omitted field can mean "inherit everything". So adapters never copy the allowlist across. They produce a true deny-by-default result:

- **Allowlist harnesses** (Claude Code `tools:`): always write the list. A missing or empty list never gets through validation.
- **Permission-map harnesses** (OpenCode `permission:`): explicit allows, plus `"*": deny` and explicit denies for every other built-in tool.
- **MCP tools**: denied by wildcard where the harness supports it. Where it doesn't, the target is marked as unable to enforce this.

Each adapter declares, per feature, whether it can **enforce**, only **approximate**, or **not support** it. If an agent needs something its target can't enforce, `install` fails for that target. Silently installing a weaker agent is the worst outcome for a tool whose point is restriction.

Features tracked: `tool_allowlist`, `mcp_deny`, `skill_preload`, `skill_restrict`, `model_select`.

### No bash in the vocabulary

Restricted agents are defined by allowlist only. agentc's tool vocabulary has no bash, because bash makes any file-level allowlist meaningless (`sed -i` is an edit).

### Model: inherit, or explicit per harness

Model IDs differ between harnesses and developers have different providers. v0 supports two forms:

1. Omit `model`: the agent inherits the developer's current model. This is the default.
2. A map of harness to concrete model ID. Unlisted harnesses inherit.

Abstract tiers (`fast`, `strong`) need a per-developer mapping file and are deferred until repeating IDs across many agents becomes a real annoyance.

### One repo per developer, user-level install

Each developer keeps their own agents repo. agentc installs into each harness's **user-level** folder, so agents work in every project. There are no project-specific agents.

`--source` should still be designed to accept several sources later (later ones overriding earlier ones), so a shared team repo can be added without restructuring.

### Symlink install, no manifest

Following wshobson/agents: generated files live in a gitignored build folder inside the developer's repo, and agentc symlinks them into the harness folders.

- Updates: `git pull && agentc install`.
- Removal: agentc owns exactly the symlinks that point into its build folder. Anything else is never touched or overwritten.
- Windows: symlinks need developer mode or admin rights. Fall back to copy plus a manifest there if needed.

Every generated file carries a header saying it was generated by agentc and where its source is, because some harnesses have their own agent editors that would otherwise edit generated output.

### Memory is a skill

No memory system in v0. Memory can be an ordinary skill. Note that writing memory requires a write tool, so only agents allowed to write files can persist memory.

### TypeScript on Bun

Similar tools are Node/TypeScript, and anything built inside the harnesses later (slash commands, pi/omp extensions) must be TypeScript anyway, so one language covers both. Bun's `bun build --compile` gives standalone binaries, which was the main argument for Go.

## Architecture

```
spec parser + validator (zod)
        │
     Agent (normalized)
        │
   ┌────┴─────┬──────────┬──────────┐
 claude   opencode      pi        omp      ← adapters
        │
  build folder → symlinks into user-level harness folders
```

Adapter interface (sketch):

```ts
interface Adapter {
  name: "claude" | "opencode" | "pi" | "omp";
  detect(): Promise<boolean>;                   // is this harness installed?
  builtinTools(): NativeTool[];                 // full inventory, for explicit denies
  capabilities(): Record<Feature, Support>;     // enforce | approximate | unsupported
  compile(agent: Agent): { files: File[]; warnings: string[] };
  installDir(): string;                         // user-level target folder
  preflight?(): Promise<void>;                  // e.g. pi: subagent extension present
}
```

## Contract tests

Per harness, against the real harness with a cheap model:

1. Spawn the compiled agent and call an allowed tool: succeeds.
2. Call a forbidden built-in tool: blocked.
3. Call a forbidden MCP tool: blocked.
4. Use the listed skill: available. An unlisted skill: blocked, or the target is marked approximate.

These tests are the real guarantee. Run them in CI on a schedule against the latest harness versions, because harness formats change often.

## Build order

0. **Verification (about half a day).** Answer the open questions below.
1. Spec schema and `agentc validate`.
2. Claude Code adapter, `install`, contract test. Proves the pipeline end to end.
3. OpenCode adapter. First permission-map target, so it stresses the abstraction.
4. pi adapter, on the chosen subagent extension.
5. omp adapter, based on step 0.

## Open questions (step 0)

- **omp:** does it read `.pi/agents/` or its own `~/.omp/agent/agents/`? Which frontmatter fields does its `task` tool honour (it is known not to use pi's `model` field)? Does a `tools:` restriction hold?
- **pi:** which subagent extension do we standardize on (the reference `examples/extensions/subagent` or `@tintinweb/pi-subagents`)? Enforcement on pi is only as good as that extension.
- **Skills:** on each harness, can skills be *restricted* per agent, or only preloaded? If most can only preload, decide whether "approximate" is acceptable for skills.
- **MCP:** on each harness, are MCP tools blocked when not on the allowlist?
- **Paths:** confirm the user-level agent and skill folders for each harness.

## Not in v0

Agent list or UI, harness plugins and slash commands, a runtime spawner, a memory system, syncing, a shared team repo, model tiers, a standard result format for subagents.
